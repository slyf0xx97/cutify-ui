Ship It

What happens to your commit between git push and production, and which bot checks it on the way.

  • Five steps, always in the same order
  • One red step stops the line before anything deploys
  • Every step leaves a log you can read

01

Push your commit

A push is the only thing that starts the line. CI notices the new commit within a few seconds and gives the run a number and a log page. Branches get lint, build and tests. Main also gets staging and production. Why: every change takes the same road, so nobody ships by hand.
You push→CI starts a run→Fuzz takes the first look
~/shop-webSample terminal
$ git commit -m "Round cart discounts to the cent"
$ git push origin main

→ run #1287 started for 9f3c2ab
What starts a run Sample team rules
  • brA push to any branch runs lint, build and unit tests. Nothing deploys.
  • mnA push or merge to main runs all five steps, ending in production.
  • 1xOne run per commit. Push twice quickly and the older run is cancelled.
02

Meet the crew

Five bots, one per step, always in this order. Each bot is a plain script with fixed rules. None of them guess, learn or use AI. Same commit in, same answer out. Every step can be run on your laptop too. Why bots: people forget a check on a Friday, scripts don't.
Fuzz lints→Bolt builds→Tick tests→Hop deploys to staging→Ship deploys to production

    Watch a red run

    Run 1287 failed one unit test. Tick marks the step red and stops. Hop and Ship never start. Staging and production keep the last good image. Your commit shows a red cross until a new push passes. Why stop: a broken change on staging is cheap, on production it isn't.

    How to read any run, in five moves
    1. Find the red stepStep headers show the name, a mark and the time. Skipped steps never ran, so ignore them.
    2. Copy the commandThe $ line is exactly what the bot ran. Run it yourself.
    3. Go to the first ✕ FAILIt names the test, the file and the line. Fix that one first.
    4. Read expected against gotThe gap between the two lines is the bug.
    5. Check the exit codeAnything but 0 stops the line. That's why Hop and Ship were skipped.
    05

    Fix it and push again

    Fix the code, not the test, unless the test is wrong. Run the failing test on your laptop first. Then push: a new commit gets a new run. Don't press re-run on a red run and hope. If a test fails only sometimes, tell the team: it's flaky. Why: a green run is the only way into production.
    You fix one line→run the test locally→push→all five go green

    How it works

    One push, start to finish. About eight minutes on a normal day. Times are typical, not promises. Why it matters: if a run takes much longer, check the log of the slow step. Typical times, sample
      Push to live, about 8:16, sample
      Who does what
      YouWrite the change, run the tests on your laptop, push, read the log when a step goes red, and fix it.
      CodeFive bots run the checks in a fixed order, stop the line on red, and deploy on green. No AI anywhere in the pipeline.
      Rules of the line Sample team rules
      • R1Steps run in order. A step starts only when the one before it is green.
      • R2One red step stops every step after it.
      • R3The image Bolt builds is the one Ship deploys. Nothing is rebuilt on the way.
      • R4Only main reaches staging and production.
